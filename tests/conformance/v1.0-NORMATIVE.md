## Why this document exists

The conformance kit ships **153 cases across 24 categories**.
Not every case is suitable as a v1.0 GA conformance gate:

* Some cases test **slice-7 interpreter** behaviour
  (`runtime-7/`) that an alternative-impl is free to handle
  differently provided the spec-prose semantics hold.
* Some cases test **backend-specific machinery** (`codegen/`,
  `native_abi/`, `wasm_component/`) that a front-end-only impl
  legitimately cannot evaluate.
* Some cases are **illustrative spec_coverage stubs** that
  exist to pin a numbered spec section to *any* fixture, not to
  carry a hard pass/fail signal.
* Some cases lean on **opt-in features** (`deterministic_replay/`
  with `STARDUST_REPLAY_*` env vars; `formatter_idempotence/`
  with the `mty fmt` subcommand specifically).

The v1.0 GA conformance claim **only requires every NORMATIVE case
in this document to pass**. INFORMATIVE cases may be skipped by an
implementation that documents *why* (typically: missing backend,
single-impl alternative that subsumes the case, opt-in feature
disabled). The kit driver SHOULD print a clear NORMATIVE / INFORMATIVE
split in its summary line so reviewers can read a one-line claim.

## Classification policy

* **NORMATIVE** — the case exercises a spec rule that every
  conforming implementation **MUST** satisfy. The case's fire-or-
  pass behaviour is implied directly by the v1.0-rc.md spec prose.
* **INFORMATIVE** — the case is **illustrative**. It pins an
  expected-behaviour shape that the spec recommends but does not
  mandate of every implementation. An impl that skips an
  informative case stays conforming; an impl that **fails** a
  case it claims to support (after running it) is NOT conforming.

## How a conforming impl reports results

A v1.0 GA conformance claim takes one of three shapes (all valid):

1. **Full conformance.** "153 / 153 cases passing (104 normative,
   49 informative)." This is the strongest claim.
2. **Front-end-only conformance.** "104 / 104 normative passing;
   49 informative skipped (no native backend, no wasm backend,
   no built-in formatter)." This is the most common claim for
   alternative impls.
3. **Targeted conformance.** "104 / 104 normative + N of 49
   informative passing." Each declared informative category MUST
   either pass every case or document why a specific case is
   skipped.

Failures — a normative case that runs but produces the wrong
diagnostic / exit code / trace — are **always** disqualifying.

## v1.x amendment policy

Within v1.x:

* A case may **move from INFORMATIVE to NORMATIVE** in a minor
  release (additive — strengthens the conformance claim). The
  release notes call out the move.
* A case may **NOT move from NORMATIVE to INFORMATIVE** in any
  v1.x release without a major-version bump — that would weaken
  the conformance contract for impls already claiming v1.0
  conformance.
* New cases added in v1.x default to INFORMATIVE for one minor
  cycle, then move to NORMATIVE if no impl objects.
